# Submission runbook

The exact steps a human takes to submit, so nobody has to re-derive them under
time pressure. This is an operator's checklist, not a pipeline component —
nothing in this file runs automatically and nothing in it should be scripted
into `src/`.

**Source of truth for the contract:** `docs/references/track1-submission-contract.md`
for Track 1 and `docs/references/track2-submission-contract.md` for Track 2.
Re-read the relevant one before a real submission — they are vendored precisely
because the challenge Space is mutable and a rushed re-derivation is exactly how
the chr-prefix mistake happens. This runbook assumes those contracts are current;
if you have any doubt, re-verify against the Space's raw source files the way
those documents describe, before trusting the checklist below.

**Two repos. Only one of them is gated:**

| Name | Type | Repo ID | Access |
|---|---|---|---|
| Challenge Space (submit + leaderboard) | Space | `SageBio/rare-disease-real-kid-mva-hackathon-2026` | sign-in only |
| Challenge data | Dataset | `SageBio/mva-hackathon-2026-data` | **gated — accept terms** |

The HF API reports `"gated": false` for the Space; an earlier version of this
file claimed both were gated and sent operators looking for a terms click that
does not exist. Visit the dataset URL while logged in and accept its terms:
- `https://huggingface.co/datasets/SageBio/mva-hackathon-2026-data`

Access is per-HF-account. If a teammate hits a 403/"gated" error on the
*dataset*, it means *their* account has not clicked through the terms yet —
that's an individual step, not a one-time team step.

## 1. One-time setup

### 1.1 Install the `hf` CLI

Already done for this checkout (`uv tool install "huggingface_hub[cli]"` —
lands in `~/.local/bin`, which is already on `PATH`). If setting up a new
machine:

```bash
uv tool install "huggingface_hub[cli]"
hf --version
```

Fall back to `pipx install "huggingface_hub[cli]"` or `brew install huggingface-cli`
if `uv tool install` is unavailable. Verify with `hf --version`.

### 1.2 Authenticate

Two equivalent options — pick one:

**Option A — interactive login (persists across shells):**

```bash
hf auth login
```

Paste a token from `https://huggingface.co/settings/tokens` when prompted.
A `read`-scope token is enough to download the gated dataset; you do not need
`write` unless you plan to `hf upload` something yourself.

**Option B — environment variable (scoped to one shell/session, nothing written to disk):**

```bash
export HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Either way, confirm with:

```bash
hf auth whoami
```

It should print your HF username. If it prints "Not logged in", authentication
did not take — retry option A or B before going further. **Never put a token
in a repo file, a commit, or `env.example`** — it goes in `.env` (gitignored)
or your shell's own environment only, consistent with this repo's existing
credential handling (see `docs/privacy-model.md`).

### 1.3 (If needed) download the gated data

```bash
hf download SageBio/mva-hackathon-2026-data --repo-type dataset --local-dir <somewhere-outside-the-repo>
```

Download this **outside the repo tree**, same rule as any other patient-derived
asset (`docs/privacy-model.md`, GP-40). Do not download into `mva-research/`.

**Important distinction:** `hf auth login` authenticates the CLI for
downloading/uploading repo files. It does **not** log you into the Space's web
page — that Gradio app uses its own HF OAuth "Sign in" button, which you click
separately in the browser using the same HF account. You need both: CLI auth
to pull the gated dataset, browser auth to use the Submit tab.

## 2. Where the submission CSV lives

The submission CSV is **not** a repo artifact. It is generated by your pipeline
run against real patient data and lives on the encrypted external workspace
(`$MVA_WORKSPACE`), never inside `mva-research/`, never committed, never
attached to an issue or chat.

This runbook deliberately does **not** hardcode or guess that path — it is
operator-supplied and changes per run. To find it:

```bash
echo "$MVA_WORKSPACE"
```

then locate the CSV under whatever output layout your own run used (e.g. a
`runs/<run-id>/submission/` style directory, if that's the convention your
pipeline follows). Do not browse `/Volumes/` looking for it — you should
already know the path from having produced it. If you don't, regenerate it
from your run's own logs/manifest rather than guessing at filenames on a
mounted encrypted volume.

Two files besides the CSV are also required for Track 1 (and analogous ones
for Track 2 — see §5): a **report**, PDF or Markdown only, and a **public
GitHub URL**. Keep the report file itself outside the repo too if it embeds
any real coordinates; a repo-safe report should describe method and rationale
without literally listing patient variants (`docs/privacy-model.md`, PRIV-10/13).

## 3. Pre-flight checklist — run this before every submission

Every item below is a hard-fail in the scorer if violated, verified directly
against `evaluation.py`. Check all of them, every time, even on attempt 6.

- [ ] **`proband_id` is exactly `PROBAND01`** on every row. Anything else, or a
      stray extra proband, hard-fails the *entire* submission (the scorer only
      evaluates the first proband it encounters in the file).
- [ ] **Every chromosome is `chr`-prefixed** (`chr1`, not `1`; `chr15`, not `15`)
      — in both `chrom_1` and `chrom_2` wherever `chrom_2` is populated. The
      scorer compares chromosome strings with `.strip()` only — **no chr-prefix
      or case normalisation**. A correct answer submitted as bare `15` scores
      **zero** on both metrics while looking right to a human reader. This is
      the single highest-consequence formatting detail in the whole submission.
- [ ] **At most 10 rows** (no minimum). More than 10 raises a hard error.
- [ ] **Every `epcr` is in `(0, 1]`** — strictly greater than 0, at most 1 —
      and **all `epcr` values in the file are distinct**. A tie pulls a wrong
      row into the winning threshold's prediction set (F-max falls from 1.0 to
      0.667), and if the tied wrong row happens to sit first in the file it
      also steals rank 1, costing a further 50 rank points. Strict separation
      is free — it doesn't cost you anything to make every value unique.
- [ ] **A compound-het pair is ONE row**, using the `_2` columns
      (`chrom_2,pos_2,ref_2,alt_2`) — never split across two single-variant
      rows. Splitting is a common mistake that still gets full F-max but drops
      rank points from 100 to 50, because the scorer requires
      `row.variants == true_variants` as one frozenset, and only checks for a
      partial match if no row achieves that.
- [ ] **Header present, exact column order:**
      ```
      proband_id,chrom_1,pos_1,ref_1,alt_1,chrom_2,pos_2,ref_2,alt_2,epcr,finding_type,notes
      ```
- [ ] **Coordinates are GRCh38**, and match the representation in the source
      VCF verbatim — do not renormalise an indel before submitting; the scorer
      matches `(chrom, pos, ref, alt)` literally.
- [ ] **`finding_type`**, if set, is `primary` or `secondary` (anything else is
      a hard error). Blank defaults to `primary`.
- [ ] Fill unused row budget with your next-best lower-EPCR candidates rather
      than leaving rows out — a lower-EPCR row can never displace a higher one
      on either metric, so an unused row is pure forfeited upside, never risk.

A quick structural self-check (run against your own CSV, path supplied by you —
nothing here is patient-data-specific beyond the file you already have open):

```bash
python3 - "$SUBMISSION_CSV" <<'PY'
import csv, sys

path = sys.argv[1]
EXPECTED_HEADER = [
    "proband_id", "chrom_1", "pos_1", "ref_1", "alt_1",
    "chrom_2", "pos_2", "ref_2", "alt_2", "epcr", "finding_type", "notes",
]

with open(path, newline="") as f:
    reader = csv.DictReader(f)
    assert reader.fieldnames == EXPECTED_HEADER, f"header mismatch: {reader.fieldnames}"
    rows = list(reader)

assert len(rows) <= 10, f"{len(rows)} rows, max is 10"

epcrs = []
for i, row in enumerate(rows, 1):
    assert row["proband_id"].strip() == "PROBAND01", f"row {i}: bad proband_id {row['proband_id']!r}"
    for col in ("chrom_1", "chrom_2"):
        c = row[col].strip()
        assert c == "" or c.startswith("chr"), f"row {i}: {col}={c!r} not chr-prefixed"
    e = float(row["epcr"])
    assert 0 < e <= 1, f"row {i}: epcr {e} out of (0,1]"
    epcrs.append(e)
    ft = (row.get("finding_type") or "primary").strip().lower()
    assert ft in ("primary", "secondary"), f"row {i}: bad finding_type {ft!r}"

assert len(epcrs) == len(set(epcrs)), "duplicate epcr values present — break the tie"
print(f"OK: {len(rows)} rows, all checks passed")
PY
```

This checks structure only. It cannot tell you whether a compound-het
candidate should have been paired into one row instead of two separate rows
— that's a judgment call about what you *meant* to submit, not something a
column check can catch. Re-read the row list once by eye for that.

## 4. Submitting — Track 1

1. In a browser, go to
   `https://huggingface.co/spaces/SageBio/rare-disease-real-kid-mva-hackathon-2026`
   and sign in with your HF account (the Space's own "Sign in" / OAuth button
   — separate from the CLI login in §1.2).
2. Open the **"Submit - Track 1"** tab.
3. Fill in:
   - **Team / Display name** (optional — leave blank to use your HF username;
     if submitting as a team, every teammate must use the *exact same* name so
     entries group together on the leaderboard).
   - **GitHub repo URL** — must start with `https://github.com/`, public.
   - **Report file** — `.pdf` or `.md` only.
   - **Predictions CSV** — the file you validated in §3.
4. Click **Submit & Score**. You get an immediate score (rank points, F-max)
   back in the page — this is the automated component only; method/report
   quality is judged separately.
5. The page shows a running quota: `<used> / 6 submissions`. Only your
   **highest-scoring** submission counts toward the leaderboard, not your most
   recent one.

**Strategy note:** six Track 1 attempts are allowed and the best one counts.
There is no reason to hold back a submission you believe is valid — bank it
early, then keep improving and resubmit. A conservative first submission
(e.g. panel-gene tier-1/tier-2 candidates only) locks in a floor score at zero
cost; nothing about submitting early forecloses a better attempt #2–6 later.

## 5. Submitting — Track 2

Verified against the Space's own source on 2026-08-28. Full detail, with file
and line for every claim, is in `docs/references/track2-submission-contract.md`.
Judged on Scientific Rigor (35%), Potential Impact (25%), Innovation (25%),
Scalability (15%).

### The five fields, in the order the form declares them

| # | Field | Required | What actually validates |
|---|---|---|---|
| 1 | Team / Display Name | optional | none — **but blank publishes your slugified HF username** instead of the team name |
| 2 | GitHub repo URL | **yes** | `startswith("https://github.com/")` — exact, case-sensitive |
| 3 | Pitch video URL | **yes** | non-empty after strip. That is the whole test |
| 4 | Notes for judges | optional | none |
| 5 | Report file | **yes** | suffix in `{.pdf, .md}`. No size limit in the source |

Fields 1 and 4 are easy to miss; neither appeared in the earlier version of this
section.

### What is not checked, and therefore must be checked by a human

- **That the GitHub URL is public and resolves.** Only the prefix is tested. A
  private repo, a 404, or a bare `https://github.com/` all pass. Open it in a
  private browser window.
- **That the video URL is a video, plays, or is within three minutes.** Nothing
  in the code looks at it. "YouTube or Vimeo" appears only in instruction text.
- `http://`, `www.github.com`, `GitHub.com` and SSH URLs are **rejected** — the
  prefix test is case-sensitive.

### The methods description — the largest single requirement

The tab serves `static/templates/methods_description_form.xlsx`. Its **"Track 2
methods"** sheet asks ten questions and states that submissions without a methods
description "may be judged less favorably on the **Scientific Rigor and
Innovation** criteria" — **60% of the rubric**. There is no upload slot for the
workbook, so the answers must be **inside the report**. Question 10 is a
**≤500-word method abstract including strengths and limitations** — the only word
limit anywhere in the submission.

The report must also characterize the variant mechanism; that is a stated content
requirement, not a stylistic suggestion.

### Attempt mechanics — the parts that decide whether one click is fatal

- **One attempt, genuinely enforced**, keyed **per HF username** — not per team,
  despite the workbook saying "one final submission per team".
- **A rejected submit does not burn the attempt.** Validation failures are free;
  only a fully valid payload consumes it. Deliberately failing validation first
  is therefore a safe way to smoke-test the form.
- **The guard fails open** on an HF API error, so a transient failure could let a
  second submission through. Do not rely on it to protect you.
- **The write is not atomic.** Metadata commits *before* the report uploads, with
  no rollback. A failed report upload leaves you at 1/1 **with no report
  attached**. Upload on a stable connection; this is the worst failure mode here.
- **The report filename is stored verbatim** as a git path component — Track 1
  sanitises, Track 2 does not. Use plain ASCII, no spaces, and embed the team or
  HF username in it.
- **The `0 / 1` status card does not refresh after a successful submit.** The
  confirmation block is the only receipt. Do not read the stale card as a failure
  and resubmit.

### There is no deadline in the code

`CHALLENGE_ACTIVE` is a hand-flipped boolean in `config.py`. `datetime.now()`
appears twice in the Space and both are `strftime` stamps — never compared to
anything. The published "October 24 (23:59 UTC)" is display text in `about.py`,
two lines under "Dates are subject to change". **Treat the date as an upper bound
that may move earlier, not a countdown to run down.**

## 7. If something looks wrong at submission time

- **"Unknown proband_id" error** — you have a row with anything other than
  `PROBAND01`, or a leftover header/blank row being parsed as data. Check for
  stray whitespace or a second proband slipped into the file.
- **Score is unexpectedly 0.0** — check chromosome prefixes first. This is the
  most common way a correct answer scores nothing (see §3).
- **"Proband has N rows; max is 10" error** — trim the file; there is no
  minimum, so removing low-value rows costs nothing on the metrics that
  matter (F-max/rank points can't be hurt by rows you don't submit).
- **Quota already at 6/6** — that account is done for Track 1; per-teammate
  quotas are independent, so a teammate with remaining quota can still submit
  under their own account if the team wants another attempt banked (though
  only the best across however you've organised submissions is what surfaces
  on the leaderboard entry for your team name).
- **Gated-access errors on the dataset** — re-check the "both need accepted
  terms" note at the top of this file: the terms must be accepted by the
  specific HF account that's running `hf download`/logging in, not just any
  team member.
