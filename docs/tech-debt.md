paying it down. Ordered by that cost, not by effort.

| TD-06 | Network denial is Python-level only, and the structural test cannot see the one child process that matters | `mva.privacy.netguard` is a `sys.addaudithook` tripwire, not a boundary: C extensions (`pysam`/htslib, `cyvcf2` — the primary genomics I/O path) call `connect(2)` from C and emit no audit event, `ctypes` reaches libc directly, and audit hooks are per-interpreter so a spawned child is unpoliced. The gap is not hypothetical. `annotation/snpeff_local.py:1600` spawns a JVM and hands it a VCF of **proband coordinates on stdin**; `-nodownload/-noStats/-noLog` constrain SnpEff's *expected* behaviour and are flags to a cooperative program, not a boundary around an uncooperative one. `OfflineProfile(strict=True)` would block the spawn, but the pipeline runs non-strict by default (`orchestrator.py:181`) because strict also blocks the `git` calls the provenance manifest needs — so the guard neither can nor does stop it. The structural test (`test_no_network_clients_in_sensitive_stages`) now forbids `socket`/`ssl`/`asyncio`/`ctypes`/`cffi`/`subprocess`/`importlib` in addition to the seven client roots, and pins the subprocess exemption to that one file with its reason, so the exposure cannot grow silently — but a lint over import statements cannot observe a child process, cannot observe C code, and cannot observe a run. Its docstring now says so. `NetworkProfile.OFFLINE_ENFORCED` remains the operator asserting an OS control, never an observation. | Before the first real-data run. The feasible macOS control is `sandbox-exec` with a Seatbelt profile denying `network-outbound`, wrapped around the whole `mva run` invocation so the JVM inherits it — a child cannot escape its parent's sandbox, which is exactly why the wrapper has to be outside the Python process rather than inside it. Deprecated by Apple but functional on the target machine; a `pf` deny rule for the run user is the non-deprecated equivalent, and the Wi-Fi switch is the control that never has a bug. Whichever is used, `OFFLINE_ENFORCED` should stay an assertion until something in the run can actually verify it. |

| TD-12 | Container base image is not digest-pinned | `workflow/containers/Dockerfile` carries a `<PASTE HERE>` placeholder rather than a fabricated digest. The image is reproducible by tag only. | Before using the container for a reproducibility claim. |
| TD-13 | Repeat expansions are invisible | Short-tandem-repeat expansions are not called, not represented and not scorable. The pipeline reasons over VCF SNV/indel records only, so an expansion at a candidate locus is not down-ranked — it is absent, and a negative result cannot distinguish "no expansion" from "never looked". Repeat-mediated disease is a real class of paediatric neurodevelopmental phenotype. | Before treating a negative result as informative — pair with TD-03, which is the same "we cannot see this variant class at all" gap. | TD-17 | `knowledge/real/gene_phenotype.tsv` carried the wrong quantity in `association_strength` — **FIXED, ADR 0021** | The column named `association_strength` held none: it held HPO's phenotype-FREQUENCY vocabulary (47,097 × `HP:0040283`, 35,110 × `HP:0040282`, 19,201 × `HP:0040281`, ~6,996 × `HP:0040284`, 337 × `HP:0040280`, tens of thousands of `n/m` fractions and percentages, and 31,169 empty where HPO recorded `-`). The empty cells were the symptom, not the defect — the generator's docstring said it was writing frequency, the reader validated the same column as curated gene-disease evidence strength and weighted it 1.0/0.8/0.6/0.4, and two modules agreed on a column name while disagreeing about what it meant. `GenePhenotypeIndex.from_tsv` refused the whole file on its first row, correctly: a lenient reader would have weighted "occurs in 5–29% of cases" as "definitively curated". The table was dead — no code path could use it, and the real-data phenotype ranking had to be computed against the HPO release directly. | **Paid down 2026-08-28 (ADR 0021).** Frequency moved to its own `hpo_frequency` column with its own parser and vocabulary; `association_strength` now carries real ClinGen/DDG2P clinical validity with `association_strength_source` naming the panel; absence is representable and weighted at the explicitly named `UNCURATED_ASSOCIATION_WEIGHT`. The table loads: 221,789 rows over 3,634 genes. Remaining, tracked as TD-20: the validity column is GENE-level, not (gene, disease). |
| TD-14 | mtDNA heteroplasmy is not measured | `chrM` calls are now modelled as `InheritanceModel.MITOCHONDRIAL` rather than being mislabelled homozygous-recessive, but the quantity that decides whether an mtDNA variant matters — the heteroplasmy fraction, and whether the sampled tissue is the affected one — is neither computed nor represented. The inheritance component is therefore scored at a flat mid-range value for every mitochondrial candidate, and a 2% heteroplasmy ranks identically to a 90% one. | Before any mitochondrial candidate is reported as a finding. Needs an mtDNA-aware caller (heteroplasmy from allele fraction at high depth), a tissue field on the sample, and a heteroplasmy-aware inheritance score. |
| TD-15 | `frequency.min_allele_number` is an unvalidated cut-point | The 2000-allele guard on the population maximum (ADR 0010) is reasoned, not fitted. A filtering allele frequency (95% CI lower bound), as gnomAD and ACMG BA1/BS1 use, is the better instrument and needs only `allele_count`/`allele_number`, both already stored. | When real gnomAD frequencies replace the synthetic table (TD-01). |
| TD-16 | Reports render the raw per-allele balance, not the site allele fraction | `evidence/store.py` and `reporting/dossier.py` write `Genotype.allele_balance` verbatim into the variant table and the dossier. Neither applies the heterozygous band to it, so no judgement is wrong — but for a record split from a multiallelic site a reader is shown 0.913 where the site fraction is 0.477, and will draw the same conclusion the scoring stage used to. | Whenever those artifacts are next touched. Fix is to render `VariantRecord.allele_fraction` alongside it, and to name which is which. Enforced-adjacent: the exemption is listed with this reason in `tests/unit/test_architecture.py`. |
| TD-18 | The evidence store still receives every ledger item | With a whole-genome ledger holding ~6.9 M items, `_persist_evidence` writes all of them into DuckDB and then exports them to Parquet, and `verify_determinism` hashes that export — twice, because `just verify` runs the demo twice. `EvidenceStore.write_evidence_stream` makes it possible within bounded memory; it does not make it cheap. | When whole-genome run time becomes the constraint. The alternative composition — ledger only the evidence of variants that survive selection — is a decision against GP-19, not an optimisation, and needs its own record. |
| TD-19 | Two concurrent runs of one case share a spill filename | `EvidenceLedger`'s spill file is `evidence-ledger-<run_id>.sqlite` under the workspace, and `run_id` is derived from the config, so two simultaneous runs of the same case would open the same path — the second unlinks and recreates it under the first. They already collide on the run directory, so this is a pre-existing property rather than a new one, but a shared run directory is an overwrite and a shared spill is a corrupted read. | Before anything runs two cases concurrently in one workspace. Fix is a pid suffix or an advisory lock at `SqliteEvidenceSpill.__init__`. |
| TD-20 | `association_strength` in `gene_phenotype.tsv` is gene-level, not (gene, disease)-level | ClinGen and DDG2P curate the (gene, DISEASE) pair; the column takes the strongest classification across all of a gene's diseases, so a gene curated `definitive` for one disease and `limited` for another reads `definitive` on the phenotypes annotated via the weaker disease. Measured, not assumed: joining each HPO annotation to the curation for its own disease reaches only 75,379 of 275,046 candidate source rows (27%), because HPO annotates against OMIM/ORPHA and ClinGen curates against MONDO with no crosswalk in the downloaded resources. The over-statement is stated in the table header and in ADR 0021, not hidden. | When a MONDO↔OMIM crosswalk is acquired (or ClinGen publishes OMIM ids). Fix is to key `curated_strength_by_gene` on (gene, disease) and fall back to gene-level only where the join fails, with the granularity recorded per row. |
| TD-21 | GP-30 byte-identity is verified only under the frozen demo clock | `pipeline.py:450` picks `demo_clock()` when `config.synthetic` is true and `SystemClock()` otherwise, and nothing in the repo ever passes the `clock` override — there is no `--clock` flag. Every determinism check (`just demo-determinism`, `tests/integration/test_determinism_cross_process.py`, the scale harness) runs `config/synthetic-case.yaml`, so all of them run frozen at `2026-01-01T00:00:00Z`. `verify_determinism` (`pipeline.py:573`) excludes whole files by suffix (`provenance.json`, `*.duckdb`) and does **not** freeze the clock or mask fields, so pointed at a real case it would report a failure on ten artifacts. The scientific content is genuinely stable — no RNG, no time-derived id or hash, total orderings, verified across `PYTHONHASHSEED` and `TZ` — but "repeat runs are byte-identical" as written is a claim about the demo. Latent trap: `interventions/safety.py:323` bakes `clock.now().date()` into rejection prose, so a future real-clock check is green within a day and red across midnight. Full artifact-by-artifact scope in `docs/handoff-integrity.md`. | Before organizers rerun a submission. Cheapest honest fix is a `--clock fixed\|system` option threaded into the already-present, never-used `clock` parameter at `pipeline.py:441`, so a reproducibility run can be frozen deliberately; second cheapest is field-level normalisation of the known time-bearing keys in `verify_determinism` instead of the whole-file suffix skip. Until one exists, GP-30 must be quoted with its scope. |
| TD-22 | The split-pair check reads gene identity from `notes`, an optional column | `_validate_split_pairs` (ADR 0023) rejects one compound-het hypothesis split across two single-variant rows, which the contract prices at 100 -> 50 rank points. Two variants are a compound heterozygote when they sit in the SAME GENE, and the challenge's twelve columns carry no gene field — so the check keys on the gene symbol `_safe_note` writes first into `notes`. Rows built by `build_submission_rows` always carry it; a hand-constructed `SubmissionRow` with empty `notes` is skipped rather than guessed at, because a false positive there would refuse a legitimate submission. So the check protects the path the pipeline actually uses and does not protect a hand-assembled file. | If anything other than `build_submission_rows` starts producing submission rows. Fix is to carry gene identity on `SubmissionRow` itself and validate at the row-object level, with the `notes`-derived reading kept as the fallback for text-only validation. |
| TD-23 | The local TSV adapters canonicalise without a reference, so repeat-tract indels still miss | ADR 0024 routed both sides of the local-table join through `mva.alleles.canonicalise_allele`, which fixes every representation difference that trimming can settle — `chr1:100 AT>AG` now joins `chr1:101 T>G`. It cannot settle left-alignment: `chr1:100 A>AT` and `chr1:104 T>TT` are the same insertion into a homopolymer and only a reference FASTA can prove it, so that join still fails and still looks exactly like 'this adapter has never heard of that variant' (GP-14). The gap is declared, not hidden — both adapters publish a `LeftAlignmentReport` reading `UNAVAILABLE_NO_REFERENCE` whenever the table holds an indel, and `test_an_indel_written_at_another_position_in_a_repeat_tract_still_misses` locks the residual miss in as a known limitation. | When the local tables stop being a synthetic substitute (TD-01). Fix is the one the gnomAD and ClinVar adapters already have: take an optional `ReferenceLookup` and pass it through `_join_key`. |
| TD-24 | `knowledge/literature/` has no entry in the privacy path allowlist | `mva.privacy.classify.classify_path` grants `PUBLIC` only to the prefixes in `_PUBLIC_PREFIXES`, and `knowledge/literature` is not one, so the BUB1B tables classify as `SENSITIVE` under the default-deny rule (ADR 0022). The effect today is nil — nothing exports them, and no lint or gate reads `classify_path` over repository files — and default-deny erring toward caution is the rule working as designed rather than failing. But a path whose classification is wrong-but-harmless is exactly the kind of thing that becomes wrong-and-harmful when someone later builds an export over it. | When `src/mva/privacy/` is next open for editing (it was owned by a concurrent workstream when these tables were added). Fix is one tuple entry plus the corresponding row in `tests/unit/test_privacy.py`'s classification table. |
| TD-25 | The tumour arm is not modelled, so a compound can only be scored for one context | A child with a chromosomal-instability cancer-predisposition syndrome has two cell populations with **opposite** therapeutic requirements. The aneuploidy-selective antiproliferatives (hydroxychloroquine, tanespimycin, metformin) are rejected here with `WRONG_DIRECTION` for the soma on precisely the evidence that recommends them against an MVA-associated tumour. The pipeline scores the soma only and says so (ASSUMPTION-DRUG-08), but "rejected" is one word doing two jobs, and a reader who takes the ranked table without the prose will read "useless in this disease" where the record means "must not be given systemically to the affected child". | Before this output is shown to anyone treating a tumour. Fix is a second `MechanismHypothesis` for the tumour context with its own target node and its own signs, and a context field on the triage call — the type system already supports it; nothing constructs it. The deciding evidence would be a therapeutic-index study against the patient's own non-tumour cells, which no catalogue field can hold. |
